## Описание решения

Скрипт `src/parse_llm_logs.py` обрабатывает JSON Lines-файл `data/logs.json`, фильтрует записи по количеству использованных токенов и рассчитывает основные метрики задержки.

Результаты работы сохраняются в папку `results/`:

* `filtered_logs.json` — записи, прошедшие фильтр по количеству токенов;
* `report.json` — итоговый JSON-отчёт с рассчитанными метриками.

Входной файл содержит по одной JSON-записи на каждой строке. Основные поля:

* `timestamp` — время вызова LLM;
* `tokens_used` — количество использованных токенов;
* `latency_ms` — задержка в миллисекундах;
* `error` — информация об ошибке, если она произошла;
* дополнительные поля, например `prompt`, `response`, `model`, могут присутствовать при необходимости.

Поля `tokens_used` и `latency_ms` могут отсутствовать.

### Запуск

Из корневой папки проекта выполнить:

```bash
python src/parse_llm_logs.py
```

После успешного запуска в консоли выводятся:

* общее количество обработанных записей;
* количество записей, прошедших фильтр;
* выбранный порог токенов;
* общее количество токенов;
* средняя задержка;
* медианная задержка.

### Обоснование порога фильтрации

Для фильтрации выбран порог `1000` токенов:

```python
TOKEN_THRESHOLD = 1000
```

Используется условие `tokens_used > 1000`, поэтому записи ровно с 1000 токенами в отфильтрованный результат не попадают.

Порог `1000` выбран потому, что он рекомендован в задании и позволяет выделить относительно ресурсоёмкие запросы. Такой фильтр помогает отдельно анализировать вызовы LLM, которые используют большое количество токенов и потенциально оказывают большее влияние на стоимость и производительность сервиса.

### Дополнительная метрика задержки

В качестве дополнительной метрики выбрана **медиана (`median`) задержки**.

Медиана показывает значение, относительно которого половина наблюдений имеет меньшую задержку, а половина — большую. В отличие от среднего значения, медиана меньше зависит от отдельных очень медленных запросов.

Например, если большинство запросов выполняется быстро, но один запрос имеет аномально большую задержку, среднее значение заметно увеличится, а медиана лучше покажет типичную задержку системы.

Поэтому в отчёте используются две метрики:

* `avg_latency_ms` — средняя задержка;
* `median_latency_ms` — медианная задержка.

### Обработка пропусков и некорректных данных

Скрипт рассчитан на работу с неоднородными JSON-логами.

* Если у записи отсутствует `tokens_used`, она не проходит фильтрацию и не участвует в расчёте суммы токенов.
* Если `tokens_used` имеет нечисловое значение, запись пропускается при фильтрации, а в `stderr` выводится предупреждение.
* Если у записи отсутствует `latency_ms`, она не исключается из результатов, но не учитывается при расчёте средней и медианной задержки.
* Если `latency_ms` имеет нечисловое значение, оно не учитывается при расчёте метрик, а в `stderr` выводится предупреждение.
* Если вместо JSON-объекта встречается другая структура, например строка, такая запись пропускается с предупреждением.
* Если входной файл пустой, программа формирует корректный отчёт с нулевым количеством записей, а для метрик задержки выводит `нет данных`.
* Если входной файл отсутствует, программа выводит сообщение об ошибке в `stderr` и завершает работу с кодом `1`.
* Если файл содержит невалидный JSON, программа выводит сообщение об ошибке в `stderr` и завершает работу с кодом `1`.

### Проверка обработки ошибок

Для проверки устойчивости были созданы дополнительные тестовые файлы:

* `data/test_invalid_tokens.json` — проверка нечислового значения `tokens_used`;
* `data/test_invalid_latency.json` — проверка нечислового значения `latency_ms`;
* `data/test_invalid_record.json` — проверка записи, которая не является JSON-объектом;
* `data/empty.json` — проверка пустого файла;
* `data/broken.json` — проверка повреждённого JSON.

Также отдельно проверялось поведение при отсутствии входного файла. В этом случае программа выводит сообщение:

```text
Ошибка: файл не найден: data/logs.json
```

и возвращает код завершения `1`.
